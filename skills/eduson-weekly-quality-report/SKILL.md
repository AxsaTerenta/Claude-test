# Недельный отчёт по качеству переговоров — Eduson

> **Главный принцип.** Оценка качества переговоров существует только рядом с выручкой. Балл без выручки, конверсии и объёма выборки — не управленческий вывод, а шум. Любое утверждение отчёта привязано к строке главной таблицы, к конкретной сделке или к заявленному числу наблюдений.

> **Второй принцип.** Отчёт читают лица, принимающие решения. Каждая фраза законченная, с подлежащим и сказуемым; каждый вывод устроен как «наблюдение → следствие для выручки → действие». Ни одного обрывка вроде «выявление и презентация».

> **Третий принцип — воспроизводимость.** Отчёт собирается детерминированным конвейером `pipeline/`. Модель пишет только тексты в `content.json`, всё остальное считают и рендерят скрипты. Это гарантирует, что отчёт для любой группы и в любом новом чате совпадёт по составу, языку, числам и оформлению.

---

## 0. Что скилл делает и чего не делает

**Делает:**

- считает результат каждого менеджера за неделю и сравнивает его со средним по группе;
- сводит выручку и качество в одну таблицу, помечает расхождения между ними;
- объясняет, почему результат ниже среднего по группе: отдельно по входящему потоку и отдельно по работе менеджера;
- собирает системные паттерны выше порога выборки и единичные наблюдения ниже него;
- выдаёт индивидуальный план развития на каждого менеджера с цитатами из его разговоров, ссылками на сделки и планом на неделю с критериями проверки;
- собирает раздел лучших практик лидера недели с цифрами и цитатами;
- рендерит HTML-страницу в оформлении дизайн-бука Eduson с кнопкой выгрузки плана развития по каждому сотруднику;
- прогоняет машинную проверку и не отдаёт отчёт, если она не пройдена.

**Не делает:**

- не выставляет уровень «критический кейс» — этого уровня в системе нет, остаются только зоны роста;
- не оценивает темы из стоп-листа (§9);
- не строит выводы по группе на единичных наблюдениях;
- не характеризует личность менеджера и не сравнивает сотрудников внутри карточки;
- не упоминает работу контакт-центра и объём проверенных записей как аргумент;
- не додумывает числа, которых нет во входных данных.

## 1. Инварианты

Нарушение любого делает отчёт непригодным. Проверяются машинно в §12.

1. **Выручка рядом с качеством.** Там, где назван балл менеджера, рядом стоят его конверсия и выручка на клиента.
2. **Число выборки при каждом обобщении.** Формулировки «у команды», «системно», «у большинства» допустимы только с подписью объёма выборки.
3. **Порог системности — строго более 4 сделок.** При 4 и менее наблюдение идёт в раздел «Единичные наблюдения».
4. **Высокий результат защищает от списка отстающих.** Менеджер с выручкой на клиента не ниже среднего по группе −5 % не попадает в отстающие ни при каком балле.
5. **Малая выборка не интерпретируется.** Менеджер с числом клиентов меньше 10 получает метку «выборка мала» и исключается из рейтинга, разборов и системных выводов.
6. **Один вывод — один уровень.** Тезис живёт либо в сводке, либо в паттерне, либо в карточке. Повтор запрещён, вместо пересказа — ссылка «Подробнее — паттерн N».
7. **Каждая находка прослеживаема.** Находка без номера сделки и этапа разговора в отчёт не попадает. Номер сделки всегда ссылка на карточку amoCRM.
8. **Стоп-лист соблюдается.** Темы §9 не упоминаются ни как риск, ни как зона роста, ни в примерах, ни в цитатах.
9. **Числа не выдумываются.** Отсутствующее поле печатается словами «нет данных».
10. **Законченные фразы.** Каждый пункт любого списка и каждая ячейка таблицы — предложение с подлежащим и сказуемым, оканчивающееся точкой.
11. **Сначала данные, потом текст.** `data.json` собирается конвейером, тексты пишутся в `content.json`, Markdown и HTML рендерятся скриптами. Рендер не вводит числа, которых нет в данных.
12. **Словарь соблюдается.** Запрещённые слова §3 не встречаются в отчёте ни разу.

## 2. Вход

### 2.1. Обязательные источники

| Источник | Содержание | Отсутствует → |
|---|---|---|
| Выгрузка метрик по менеджерам (JSON) | Менеджер, Лиды, C2, C2 Каталога, Продажи, Выручка, Ср. чек, Выручка на лид; строка `Всего` — итог группы | отчёт не собирается, скилл останавливается и сообщает причину |
| Выгрузка звонков за неделю (TXT) | блоки `### Звонок N · Менеджер · Дата`, строка `Продукт · Этап · Score · Длит.`, `Deal ID`, `Резюме`, транскрипт | качественная часть не собирается, отчёт становится количественным |

Названия полей выгрузки метрик задаются в `config.json → metrics_fields`, поэтому переименование колонок в источнике не ломает сборку. Заголовки колонок выгрузки называются как в системе (в том числе «Лиды», «Выручка на лид»), но **в тексте отчёта это всегда «клиенты» и «выручка на клиента»**.

### 2.2. Нормализация значений

- пробел и неразрывный пробел внутри числа — разделитель разрядов, удаляются: `"2 490 556"` → `2490556`;
- запятая — десятичный разделитель: `"15,9%"` → `15.9`;
- проценты хранятся в процентных единицах, не в долях;
- пустая строка, `—`, `n/a` → `null`, не ноль;
- имя менеджера — ключ соединения источников, сравнивается после обрезки пробелов. Менеджер, найденный в звонках и отсутствующий в метриках, останавливает сборку.

### 2.3. Контроль целостности

Сумма клиентов менеджеров обязана равняться клиентам строки `Всего`, сумма продаж — продажам `Всего`. Расхождение печатается в предупреждениях и разбирается до публикации.

## 3. Словарь: как отчёт говорит

Это не стилистика, а требование заказчика. Машинная проверка ищет запрещённые слова и валит сборку.

### 3.1. Запрещено

| Запрещено | Пишем |
|---|---|
| лид, лиды, лидов | клиент, клиенты, клиентов |
| выручка на лид | выручка на клиента |
| деньги, денег, деньгам | выручка |
| база, базы, базе, база сравнения | среднее по группе |
| транзакционная сделка, дуга сделки | разговор ограничен анкетой и ценой; этапы разговора |
| скоринг | оценка разговоров, балл качества |
| кластер | направление обучения |
| инверсия | расхождение балла и результата |
| критический кейс, красный флаг | зона роста |
| воронка, кейс, фидбэк, перформанс | сделка, разбор, обратная связь, результат |
| любые латинские слова, кроме названий продуктов и amoCRM | по-русски |

### 3.2. Разрешено и используется

Апсейл, триггер, дедлайн, паттерн, конверсия C2, средний чек, ОКК, amoCRM, точка Б, катализатор, дефицит. Это рабочие термины команды, они остаются.

### 3.3. Тон

- Конструкция вывода: **наблюдение → следствие для выручки → управленческое действие**.
- Пишем: «менеджеры не доводят разговор до попытки оплаты», «возражение осталось без ответа», «клиент решает по цене».
- Не пишем: ярлыков личности, «сложный клиент» как объяснение, сравнений сотрудников внутри карточки, канцелярита.
- Числа в тексте — словами там, где это порог правила («более чем четырьмя сделками», «не меньше десяти»), цифрами там, где это измерение («34 сделки», «8 439 рублей»).
- Обращение к менеджеру в третьем лице по имени: «Виктория доводит клиента до оплаты».

## 4. Конвейер: как собирается отчёт

Четыре шага, порядок строгий. Все скрипты лежат в `pipeline/`, рабочий пример входа и выхода — в `example/`.

```bash
SKILL=skills/eduson-weekly-quality-report
WORK=/tmp/okk            # рабочая папка прогона
OUT=reports/2026-07-20_2026-07-26   # куда ляжет отчёт

# 1. слой данных: разбор звонков, склейка сделок, метрики, метки, признаки этапов
python3 $SKILL/pipeline/build_data.py \
  --calls calls/2026-07-20_2026-07-26/выгрузка.txt \
  --metrics $WORK/metrics.json \
  --config $WORK/config.json \
  --content $WORK/content.json \
  --out $WORK/data.json

# 2. слой текста: Markdown + REPORT.json + CARDS.json + GAP.json
python3 $SKILL/pipeline/render_report.py \
  --data $WORK/data.json --content $WORK/content.json --outdir $OUT

# 3. слой вёрстки: страница в оформлении дизайн-бука
python3 $SKILL/pipeline/render_html.py \
  --md $OUT/REPORT.md --logo eduson-design-book/eduson-logo.png --out $OUT/index.html

# 4. машинная проверка: без неё отчёт не публикуется
python3 $SKILL/pipeline/verify.py --outdir $OUT --data $WORK/data.json --content $WORK/content.json
```

Порядок работы модели:

1. Прочитать выгрузки, разложить `config.json` (§5) и черновой `content.json` только с техническими полями: `contact_center_calls`, `category_overrides`.
2. Прогнать шаг 1 и прочитать `data.json`: числа, метки, доли этапов, список менеджеров под разбор «ниже среднего».
3. Прочитать резюме всех сделок (`data.json → deals[].summaries`) и транскрипты нужных сделок, выписать цитаты.
4. Написать тексты `content.json` по §6.
5. Прогнать шаги 2–4. Провал проверки — исправить текст или данные и перегенерировать; выдавать отчёт с непройденной проверкой запрещено.
6. Опубликовать по §11.

## 5. `config.json`

```json
{
  "team": "Анар",
  "period": {"from": "2026-07-20", "to": "2026-07-26", "label": "2026-07-20 — 2026-07-26"},
  "generated_at": "2026-07-29",
  "amo_url_prefix": "https://eduson.amocrm.ru/leads/detail/",
  "metrics_fields": {
    "manager": "Менеджер", "clients": "Лиды", "c2": "C2", "c2_catalog": "C2 Каталога",
    "sales": "Продажи", "revenue": "Выручка", "avg_check": "Ср. чек",
    "revenue_per_client": "Выручка на лид", "total_row": "Всего"
  },
  "thresholds": {"min_clients": 10, "revenue_ratio": 0.95, "okk_gap": 2.0, "pattern_deals": 4, "gap_pct": 30}
}
```

Пороги менять нельзя без прямого решения заказчика: `min_clients` — граница интерпретации, `revenue_ratio` — защита от списка отстающих, `okk_gap` — допуск по баллу, `pattern_deals` — порог системности, `gap_pct` — повод для разбора причин.

## 6. `content.json`: что пишет модель

Единственный файл, где живёт авторский текст. Все ключи обязательны, кроме помеченных.

| Ключ | Что это | Правило |
|---|---|---|
| `contact_center_calls` | номера звонков, отнесённых к контакт-центру | §7.2. В тексте отчёта не упоминаются |
| `category_overrides` | `{"46368384": "C"}` — ручные категории поверх автоматики | §7.4 |
| `theses` | 3–5 выводов недели | §6.1 |
| `divergence_intro` | абзац о природе расхождения балла и выручки | ≤ 6 предложений |
| `divergence` | по менеджеру: `score`, `money`, `where`, `quote`, `deal`, `stage`, `action` | §6.2 |
| `divergence_summary_title`, `divergence_summary` | подраздел «Как читать эти случаи» | обязателен |
| `divergence_notes` | пограничные случаи (необязательно) | массив строк |
| `gap_cases` | по менеджеру: `verdict`, `traffic[]`, `manager[]`, `excluded`, `split`, `check[]` | §6.3 |
| `gap_notes` | оговорки по тем, кого разбор не касается (необязательно) | массив строк |
| `patterns` | `key` (P1…P9), `title`, `observation`, `risk`, `action` | §6.4 |
| `single_observations` | `key`, `text` | только для признаков ≤ 4 сделок |
| `priorities` | ровно три: `title`, `why`, `target_metric`, `target_shift`, `cases[]` | §6.5 |
| `best` | `lead`, `numbers[]`, `practices[]`, `howto` | §6.6 |
| `cards` | по менеджеру: `portrait`, `strengths[]`, `gaps[]`, `plan[]`, `score` | §6.7 |

### 6.1. Выводы недели

От трёх до пяти. Каждый — о качестве переговоров, с числовым якорем и законченной мыслью. Не пересказ таблицы.

Образец:

> 1. Менеджеры не доводят разговор до попытки оплаты: в 34 сделках из 98 цена названа, но причина решить сегодня не прозвучала, и клиент ушёл думать.
> 3. Менеджеры показывают программу, не сформировав образ результата: в 26 сделках из 98 разговор свёлся к анкете и цене, поэтому клиент сравнивает школы только по стоимости.
> 5. Балл качества не показывает, доводит ли менеджер сделку до выручки: у Константиновой балл 83,5 при выручке на клиента ниже среднего по группе на 30 процентов, у Пименовой балл 66,5 при превышении среднего по группе на 91 процент.

Запрещено: вывод без числа, вывод длиннее 40 слов, вывод без точки, вывод-пересказ денежной таблицы без качественного содержания.

### 6.2. Расхождение балла и результата

Собирается для каждого менеджера с меткой `ОКК↓ результат↑` или `ОКК↑ результат↓`. Четыре обязательных поля:

- `score` — что показывает балл и на каких этапах собрана просадка или превышение;
- `money` — конверсия, выручка на клиента, доля потока и продаж;
- `where` — этап разговора, на котором возникает разрыв;
- `quote` + `deal` + `stage` — дословная реплика из этой сделки, подтверждающая разрыв;
- `action` — одно действие руководителя группы.

Подраздел «Как читать эти случаи» обязателен: он объясняет, где оценка недооценивает менеджера, а где этапы выполняются без доведения до решения.

### 6.3. Разбор «почему результат ниже среднего по группе»

Собирается автоматически для менеджеров с отклонением выручки на клиента ≤ −30 % при 10 и более клиентах. Задача раздела — отделить поток от работы менеджера.

Обязательная структура:

- `verdict` — короткий вывод одним-двумя предложениями;
- `traffic[]` — 2–4 пункта о входящем потоке: направления обучения, длительность разговоров, доля живых сделок в системе, объём потока в сравнении с коллегами;
- `manager[]` — 3–4 пункта о работе в разговоре: доли непройденных этапов против группы, категории сделок, повторные касания, балл;
- `excluded` — что потоком не объясняется;
- `split` — распределение ответственности прямым текстом;
- `check[]` — 3 проверки руководителя на неделю, каждая выполнима за час.

Правила аргументации: сравнивать только с числами из `data.json`; не использовать как довод число проверенных сделок; не упоминать финансовое положение клиентов (§9).

### 6.4. Системные паттерны

Признаки этапов считаются автоматически, ключи стабильны между неделями:

| Ключ | Этап | Что ловит |
|---|---|---|
| `P1` | Закрытие | попытки закрыть на оплату или бронь не было |
| `P2` | Следующий шаг | день и час следующего разговора не назначены |
| `P3` | Работа с возражениями | возражение принято без выяснения причины |
| `P4` | Цена | стоимость и размер скидки не названы |
| `P5` | Выяснение задачи | выяснение ограничено анкетой, задача и триггер не раскрыты |
| `P6` | Закрытие | способ оплаты не уточнён |
| `P7` | Апсейл | апсейл не предложен |
| `P8` | Резюме | задача клиента не повторена вслух |
| `P9` | Порядок разговора | блоки разговора не анонсированы |

Для каждого ключа с числом сделок больше порога пишется паттерн: `title` — что делают менеджеры (не ярлык, а действие), `observation` — механика в 2–4 предложениях, `risk` — следствие для выручки, `action` — что делает руководитель группы. Ключи ниже порога уходят в единичные наблюдения. Рендер сам печатает объём выборки и полный список сделок с разбивкой по менеджерам — вручную их перечислять не нужно.

### 6.5. Приоритеты команды

Ровно три, отсортированы по числу сделок в паттерне. Каждый содержит ссылку на паттерн, ожидаемый сдвиг конкретной метрики со сроком и три сделки для разбора.

### 6.6. Лучшие практики недели

- `lead` — кто лидер по выручке и кто по балансу выручки и качества;
- `numbers[]` — 3–4 факта с расшифровкой, откуда берётся отрыв (доля потока против доли продаж, конверсия, средний чек, доля сделок полного цикла);
- `practices[]` — 5–6 приёмов: `title`, `author`, `deal`, `stage`, `quote` (дословно, не короче 40 знаков), `effect` — что приём даёт в цифрах;
- `howto` — какие три записи руководитель разбирает на собрании и что повторяют остальные.

### 6.7. Индивидуальные планы развития

На каждого менеджера, включая тех, у кого выборка мала. Структура:

- `portrait` — 3–5 предложений: результат недели и его причина. Начинается с имени, объясняет, за счёт чего результат такой;
- `strengths[]` — 2–4 пункта: `text` (что менеджер делает), `deal`, `stage`, `quote` (необязательно), `why` (почему приём срабатывает, с числом или исходом сделки);
- `gaps[]` — 2–4 пункта: `text` (что не сделано, с долей сделок и сравнением с группой), `deal`, `stage`, `quote` (необязательно), `effect` (к чему привело), `action` (что делать), `pattern` (номер паттерна, если тема системная);
- `plan[]` — 3–4 пары «что сделать» и «как проверим»; проверка измерима на записях недели;
- `score` — абзац о том, за счёт чего вырастет балл; для лидера по баллу пишется прямо, что балл поднимать не нужно.

Для менеджера с меткой «выборка мала» в `gaps[]` кладётся один пункт-объяснение без ссылки на сделку.

## 7. Предобработка данных

Порядок строгий, выполняется скриптом `build_data.py`.

1. **Разбор выгрузки звонков.** Из каждого блока берутся номер, менеджер, дата, продукт, этап сделки, балл, длительность, номер сделки, резюме и транскрипт.
2. **Фильтр контакт-центра.** Звонок относится к контакт-центру, если совпадают два и более признака: длительность до 4 минут; в конце передача клиента дальше; нет показа программы; не названа цена; нет попытки закрытия. Такой звонок не считается нигде. Сделка, состоящая только из таких звонков, в разбор не входит. **В тексте отчёта фильтр не упоминается.**
3. **Склейка сделок.** Все звонки одного `Deal ID` — одна сделка. Балл сделки — среднее по её разговорам.
4. **Признаки этапов.** По объединённым резюме сделки размечаются ключи `P1…P9`.
5. **Категории A/B/C.** Автоматика по правилам ниже, ручные исключения — в `category_overrides`.
6. **Метрики и метки.** §8.
7. **Профили менеджеров.** Длительность сделки и разговора, доля сделок с названной ценой, доля без попытки оплаты, доли категорий, доля повторных разговоров, направления обучения.

### 7.4. Категории сделок

| Категория | Условие |
|---|---|
| **A** | менеджер выяснил задачу клиента, показал программу под неё, ответил на возражение и предложил оплатить или забронировать место |
| **B** | часть этапов проведена сильно, часть не доведена до конца |
| **C** | разговор ограничен анкетой, ценой и оформлением |
| **—** | ключевые этапы остались за пределами записи |

Правило перевеса: закрытие и показ программы весят больше выяснения. Сильное выяснение при непроведённом закрытии — это B или C, но не A. При сомнении ставится строже. Автоматика ошибается на сложных склейках, поэтому модель обязана прочитать резюме всех сделок и выписать исключения в `category_overrides`: в примере недели их 21 из 98.

## 8. Метрики, метки, пороги

| Метрика | Формула | Округление |
|---|---|---|
| Отклонение конверсии | `C2_м − C2_группы` | 1 знак, в процентных пунктах |
| Отклонение выручки на клиента | `(ВНК_м / ВНК_группы − 1) × 100` | целое, в процентах |
| Отклонение среднего чека | `(Чек_м / Чек_группы − 1) × 100` | целое, в процентах |
| Балл менеджера | среднее по его разобранным сделкам | 1 знак |
| Балл группы | среднее по всем разобранным сделкам | 1 знак |
| Отклонение балла | `Балл_м − Балл_группы` | 1 знак |

Метки, ровно пять, порядок проверок строгий:

```
клиентов < 10                         -> «выборка мала»
выручка на клиента ≥ среднее × 0,95 и балл ≥ среднее − 2  -> «эталон»
балл ≥ среднее − 2                    -> «ОКК↑ результат↓»
выручка на клиента ≥ среднее × 0,95   -> «ОКК↓ результат↑»
иначе                                 -> «зона риска»
```

Смысл: `эталон` — качество конвертируется в выручку, его сделки идут в лучшие практики; `ОКК↓ результат↑` — оценка недооценивает менеджера, обязательна строка-пояснение; `ОКК↑ результат↓` — этапы выполняются, но сделка не доводится; `зона риска` — обе оси ниже; `выборка мала` — вне интерпретации.

Пограничные случаи (например, выручка на клиента на 5,5 % ниже среднего при высоком балле) выносятся отдельным абзацем: менеджер не называется отстающим, разрыв объясняется одним этапом.

## 9. Стоп-лист: что не является риском

Не оценивается, не подсвечивается и не упоминается ни как риск, ни как зона роста, ни в цитатах: фейковые банковские дедлайны и «сгорающие» сроки; завышение дохода в заявке; указание прошлого места работы; оформление на третье лицо; формулировка «просто назовите цену»; «входим в состав Просвещения»; «подарочный курс выберете позже»; вся тема документов, «гособразца», ФРДО и лицензий; финансовые операции клиента и его платёжеспособность.

Уровень «критический кейс» упразднён. Всё, что не попало в стоп-лист, — обычная зона роста.

Цитаты для отчёта отбираются с фильтром: реплика со словами из стоп-листа не публикуется, даже если она удачно иллюстрирует приём.

## 11. Оформление и публикация

### 11.1. Дизайн-система

Страница собирается по дизайн-буку Eduson (`eduson-design-book/index.html`). Токены и приёмы:

- цвета: жёлтый `#ffd53b`, чернила `#1e1e20`, фиолетовый `#6b5eec`, бумага `#fffdf8`, бежевый `#f1ede5`, линия `#d9d4cb`, приглушённый `#77736d`, рост `#2eb872`, падение `#ef5268`;
- шрифты: Inter Tight для заголовков и чисел, Inter для текста, JetBrains Mono для подписей и меток;
- основной приём — обводка `2px solid #1e1e20`, скругления только `999px` на пилюлях;
- герой: жёлтый блок с сеткой 88 пикселей, рамка с логотипом, тёмный бейдж отдела, заголовок с фиолетовым курсивом, mono-кикер «команда · период»;
- разделы: круглый жёлтый индекс `01…11`, mono-надзаголовок «Раздел NN», дисплейный заголовок;
- показатели: плитки с mono-подписью, крупным числом и отклонением-пилюлей в зелёном или красном;
- цитаты: карточка с фиолетовой шапкой «Цитата из разговора» и mono-подписью со ссылкой на сделку;
- пояснения: строки «ключ — значение», ключ mono-капсом фиолетовым;
- таблицы: тёмная липкая шапка, чередование строк, моноширинные цифры, отклонения второй строкой в ячейке;
- разделы с третьего свёрнуты в `details`, кнопка «Развернуть» справа в шапке раздела;
- логотип встраивается как `data:` — файл в репозитории лежит с расширением `.png`, но внутри WebP, и по ссылке браузер его не показывает;
- у каждого плана развития кнопка «Выгрузить ИПР»: собирает самостоятельный HTML-файл с шапкой, стилями и планом сотрудника целиком на стороне браузера.

Менять оформление между неделями нельзя: страница узнаётся с первого экрана.

Папка периода называется `ГГГГ-ММ-ДД_ГГГГ-ММ-ДД`. Коммит содержит только папку отчёта. После push страница доступна по адресу `https://<владелец>.github.io/<репозиторий>/reports/<период>/`.

## 12. Машинная проверка перед выдачей

`verify.py` останавливает публикацию, если нарушено хотя бы одно правило:

**Словарь.** Запрещённые слова §3.1 не встречаются; латиница вне названий продуктов отсутствует.

**Язык.** Каждый вывод недели содержит число, оканчивается точкой и не длиннее 40 слов; каждый пункт паттерна, разбора, плана развития и разбора «ниже среднего» содержит сказуемое и точку.

**Пороги.** Каждый паттерн подтверждён более чем четырьмя сделками; каждое единичное наблюдение — четырьмя и менее; разбор «ниже среднего» собран только при отклонении ниже −30 %; у менеджера с меткой `ОКК↓ результат↑` есть строка-пояснение.

**Достоверность.** Суммы клиентов и продаж сходятся со строкой `Всего`; у каждого зачётного менеджера есть балл; все цитаты и примеры ссылаются на сделки из выборки.

**Прослеживаемость.** Число ссылок на сделки не меньше числа разобранных сделок; в каждом паттерне перечислены все его сделки.

**Форма.** Все разделы §10 присутствуют в заданном порядке.

**Вёрстка.** В HTML есть плитки, карточки цитат, карточки планов развития по числу менеджеров, кнопка выгрузки, встроенный логотип и свёрнутые разделы с третьего.

Ручная проверка, которую машина не сделает: карточку любого менеджера можно переслать сотруднику без правок; ни один вывод не повторяется в двух разделах; цитаты не содержат тем стоп-листа.

## 13. Поведение при неполных данных

| Чего нет | Что делает скилл |
|---|---|
| поблочной оценки разговоров | таблица блоков не строится, печатается таблица долей непройденных этапов из разбора сделок |
| отчёта прошлой недели | сравнение с прошлой неделей не приводится |
| плана продаж | сравнение ведётся со средним по группе |
| транскриптов | отчёт становится количественным, разделы с цитатами не собираются, об этом сказано в первом абзаце |
| отметок времени в записях | находка привязывается к номеру сделки и этапу разговора |
| эталонных разговоров по направлению | оценка ведётся по общей рубрике |

Общее правило: недостающее констатируется вслух. Тихая подстановка правдоподобных чисел — худший исход, потому что отчёт используется для управленческих решений.
